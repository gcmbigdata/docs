Esto aplica para proyectos que tienen PM2 o son estáticos. Cuando se realiza un cambio en un proyecto independiente, debe seguirse un procedimiento controlado para garantizar que la nueva versión quede correctamente desplegada y validada.

## Flujo general de actualización

<Steps>
  <Step title="Developer">
    El desarrollador realiza los cambios correspondientes en el proyecto.
  </Step>
  <Step title="GitHub — Big Data">
    Los cambios son enviados al repositorio correspondiente en GitHub.
  </Step>
  <Step title="Actualizar el proyecto en el servidor">
    Se identifica el proyecto que debe actualizarse y se procede según su tipo de despliegue.

    <Tabs>
      <Tab title="Proyecto estático">
        1. **Git pull**: traer el nuevo código al servidor.
        2. **Instalar dependencias**: si el proyecto requiere nuevas dependencias, estas deben instalarse antes de generar la versión final.
        3. **Build**: ejecutar el proceso de compilación correspondiente al proyecto.

        Por ejemplo:

        ```bash
        pnpm build
        ```

        El comando exacto dependerá de la tecnología y configuración de cada proyecto.
      </Tab>
      <Tab title="Proyecto con PM2">
        ## Antes (todo manual por SSH)

        **Actualizar un proyecto:**

        ```bash
        ssh servidor
        cd /ruta/proyecto
        git pull
        pnpm build
        pm2 restart app --update-env
        ```

        **Crear un proyecto nuevo:**

        ```bash
        ssh servidor
        cd /ruta/proyectos
        git clone git@github.com:org/repo.git   # requería deploy key o PAT en el server
        pnpm install && pnpm build
        pm2 start ecosystem.config.js
        ```

        ## Ahora (con la integración de GitHub)

        **Setup único:** conectás tu cuenta en `/github`, instalás la GitHub App seleccionando los repos. Listo, no hay claves SSH ni PATs guardadas en el servidor.

        **Crear proyecto (Import):**

        Desde la UI `/github` → clic en **Import** sobre el repo. El pipeline corre solo (`GitHubImportPipelineService`):

        | Paso | Qué hace | Equivalente manual |
        | --- | --- | --- |
        | `clone` | `git clone --depth 1` con token de instalación embebido en la URL (válido 1h) | `git clone` |
        | `install` | Detecta package manager (pnpm/bun/npm por lockfile) e instala | `pnpm install` |
        | `build` | Corre `build` si existe el script (o comando custom que configures) | `pnpm build` |
        | `ecosystem` | Detecta archivos `ecosystem.config.*` del repo | buscarlos a mano |
        | `pm2-start` | `pm2 start ecosystem.config.js --update-env` | `pm2 start` |

        Bonus: si pnpm pide aprobación de builds nativos, te lo detecta y tienes un botón para `pnpm approve-builds --all`.

        **Actualizar proyecto:** dos caminos desde la UI, sin tocar el server:

        1. **Manual:** botón de update/deploy → ejecuta el mismo pipeline pero con `git pull` en vez de clone (`deploy.service.ts`: _git pull → install → build → pm2 restart --update-env_). <img src="/images/image-5.png" alt="Image" title="Image" />

        2. **Auto-deploy:** habilitás auto-deploy por proyecto (`autoDeployEnabled` \+ `deployBranch` \+ `targetPath`). Cada `git push` a esa rama dispara el webhook → se encola un deployment → corre el pipeline automáticamente, con registro de deployments (commit SHA, logs, idempotencia por delivery ID).

        ![Image](/images/image-6.png "Image")

        ## La diferencia de fondo

        Lo que cambia conceptualmente es **quién hace el trabajo y cómo se autentica git**:

        - **Antes:** Tu eras el deploy system. La autenticación era estática (deploy keys/PATs permanentes en el server).
        - **Ahora:** PM2 View es el deploy system. La autenticación es dinámica, `git-auth.provider.ts` mintea tokens de instalación de corta vida (1h) por operación, scopeados al repo. Si revocás la instalación, todo deja de funcionar al instante sin rotar claves.

        Lo único que sigue manual: configurar variables de entorno del proyecto (`.env`) y elegir el ecosystem file en el paso final del import.

      </Tab>
      <Tab title="Proyecto no estático (no JavaScript)">
        Para proyectos que no son estáticos ni de JavaScript (por ejemplo, Python), debes realizar el paso manual que requiera la tecnología del proyecto. El flujo general es:

        ```bash
        ssh servidor
        cd /ruta/proyecto
        git pull
        # <paso que corresponda según la tecnología>
        # Ejemplos:
        #   Python:  pip install -r requirements.txt
        #   Go:      go build ./...
        pm2 restart app --update-env
        ```

        El paso intermedio dependerá del lenguaje y del gestor de dependencias del proyecto.
      </Tab>
    </Tabs>
  </Step>
  <Step title="Validar la aplicación">
    Finalmente, comprobar que la aplicación funciona correctamente. La validación debe incluir, cuando corresponda:

    - Acceso mediante la URL correspondiente.
    - Funcionalidades principales.
    - Logs de la aplicación.
    - Estado del proceso PM2.
    - Estado de los contenedores Podman, si el proyecto los utiliza.
    - Respuesta de las APIs.
    - Ausencia de errores críticos.
  </Step>
</Steps>

## Flujo resumido

```text
Developer
   ↓
GitHub — Big Data
   ↓
Actualizar proyecto
   ↓
¿Proyecto estático?
```

- **Sí** → Actualizar código → Instalar dependencias → Build → Validar aplicación
- **No** → PM2 View → Seleccionar proyecto → Deploy → Validar aplicación

<Warning>
  Después de una actualización es importante verificar tanto:

  1. El estado del proceso PM2.
  2. El estado de los contenedores Podman, si existen.

  Una aplicación puede aparecer como **online** en PM2 y aun así estar funcionalmente degradada debido a una dependencia externa caída.
</Warning>
