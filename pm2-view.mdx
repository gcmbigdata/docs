## Pasos para desarrollar y desplegar una nueva funcionalidad

<Steps>
  <Step title="Crear y preparar el repositorio">
    Crea un **fork** del repositorio de `pm2-view` y súbelo al repositorio de la organización de **Big Data**, o al repositorio de la organización que corresponda para la funcionalidad que vas a desarrollar.

    El objetivo es que la nueva funcionalidad quede asociada al repositorio de la organización y pueda ser utilizada posteriormente por el servidor de RPATIC.
  </Step>
  <Step title="Configurar las variables de entorno">
    Agrega en tu archivo `.env` las variables de entorno que necesite la nueva funcionalidad.

    Estas variables serán gestionadas mediante **INFISICAL**. No te preocupes si todavía no conoces INFISICAL; más adelante en esta documentación se explica **qué es, cómo funciona y cómo utilizarlo**.

    <Warning>
      No debes subir al repositorio valores sensibles o secretos directamente dentro del archivo `.env`. Las variables y secretos correspondientes deben gestionarse mediante INFISICAL.
    </Warning>
  </Step>
  <Step title="Crear una rama para la nueva funcionalidad">
    Antes de comenzar el desarrollo, crea una rama específica de acuerdo con la funcionalidad que vas a realizar.

    ```bash
    git switch -c feature/nombre-de-la-funcionalidad
    ```

    Esto permite mantener aislados los cambios de la nueva funcionalidad y facilita posteriormente su revisión e integración.
  </Step>
  <Step title="Desarrollar la funcionalidad">
    El desarrollo de la nueva funcionalidad se realiza en tu **PC de desarrollo local**, no directamente en el servidor de RPATIC.

    Realiza los cambios necesarios, prueba la funcionalidad y asegúrate de que todo funcione correctamente en tu entorno local.

    Una vez finalizados los cambios, realiza los commits correspondientes:

    ```bash
    git add .
    git commit -m "feat: descripción de la funcionalidad"
    ```
  </Step>
  <Step title="Configurar el repositorio en el servidor RPATIC">
    En el servidor de **RPATIC** (más adelante se explicará cómo conectarse) debes dirigirte al directorio del proyecto:

    ```bash
    cd ~/Documents/projects/pm2-view
    ```

    La **primera vez** que se configure el repositorio para este flujo, debes hacer que el `origin` del servidor apunte al fork o repositorio de la organización donde se publicarán los cambios.

    Si el repositorio ya tiene configurado un `origin`, **no debes agregar un nuevo remote**. Debes reemplazar la URL del `origin` existente:

    ```bash
    git remote set-url origin [URL-del-fork-o-repositorio]
    ```

    Por ejemplo:

    ```bash
    git remote set-url origin https://github.com/usuario/pm2-view.git
    ```

    Puedes verificar que la configuración sea correcta con:

    ```bash
    git remote -v
    ```

    <Info>
      Esta configuración se realiza en el servidor de RPATIC, pero el desarrollo y el `git push` se realizan desde tu **PC local**.
    </Info>
  </Step>
  <Step title="Enviar los cambios al repositorio">
    Desde tu PC de desarrollo, una vez que hayas terminado y commiteado la funcionalidad, envía la rama al repositorio:

    ```bash
    git push origin [nombre-de-la-rama]
    ```

    Por ejemplo:

    ```bash
    git push origin feature/nueva-funcionalidad
    ```

    A partir de este momento, los cambios estarán disponibles en el fork o repositorio de la organización.
  </Step>
  <Step title="Actualizar la aplicación desde PM2 View">
    Una vez que hayas enviado tus cambios al repositorio, accede a la interfaz de **PM2 View**: [https://gcmbigdata.online/pm2](https://gcmbigdata.online/pm2)

    Desde allí, haz clic en el botón **Update** del proyecto correspondiente.

    El botón **Update** se encargará automáticamente de realizar en el servidor las operaciones necesarias para actualizar la aplicación:

    ```bash
    git pull
    pnpm i
    build
    pm2 restart --update-env
    ```

    De esta manera, **no necesitas conectarte nuevamente al servidor para ejecutar estos comandos manualmente**.

    <Frame>
      ![Botón Update en la interfaz de PM2 View](/images/pm2-view-update-button.png)
    </Frame>
  </Step>
  <Step title="Flujo resumido">
    **Primera configuración:**

    1. Crear un fork y subirlo al repositorio de la organización correspondiente.
    2. Configurar las variables de entorno y gestionarlas mediante INFISICAL.
    3. Crear una rama para la nueva funcionalidad.
    4. Desarrollar y probar la funcionalidad en tu PC local.
    5. Configurar el `origin` del proyecto en el servidor RPATIC para que apunte al repositorio correspondiente.

    **Para cada nueva funcionalidad:**

    1. Crear una rama.
    2. Desarrollar y probar los cambios en el PC local.
    3. Hacer commit de los cambios.
    4. Hacer `git push origin [rama]`.
    5. Ir a PM2 View.
    6. Hacer clic en **Update**.
    7. PM2 View ejecutará automáticamente `git pull`, `pnpm i`, `build` y `pm2 restart --update-env`.

    <Note>
      El paso de configuración del `origin` en RPATIC solo es necesario cuando se configura por primera vez o cuando se necesita cambiar el repositorio de destino. Si ya está apuntando al repositorio correcto, no es necesario modificarlo nuevamente.
    </Note>
  </Step>
</Steps>

## ¿Qué permite hacer PM2 View?

PM2 View centraliza varias tareas operativas que normalmente realizaríamos directamente mediante la CLI de PM2.

### Visualización de proyectos

Permite consultar los proyectos actualmente administrados por PM2 y conocer su estado. Esto facilita identificar rápidamente:

- Procesos activos.
- Procesos detenidos.
- Procesos con problemas.
- Estado general de las aplicaciones.

### Logs

Permite consultar los logs de los procesos sin necesidad de acceder constantemente a la terminal. Esto resulta especialmente útil durante:

- Despliegues.
- Diagnóstico de errores.
- Validación de cambios.
- Monitorización de aplicaciones.

### Actualización desde GitHub

PM2 View permite gestionar la actualización de los proyectos cuando existen nuevos cambios disponibles en sus repositorios.

El flujo habitual consiste en:

1. Realizar cambios en el repositorio.
2. Subir los cambios a GitHub.
3. Actualizar el proyecto en el servidor.
4. Instalar cambios/dependencias si corresponde.
5. Reiniciar el proceso.
6. Revisar los logs.
7. Validar que la aplicación se encuentre funcionando correctamente.

## Auto-Deploy (webhook de GitHub)

Además del botón **Update** manual, PM2 View soporta **despliegue automático**: cuando GitHub envía un evento `push` sobre el repo y rama configurados, PM2 View ejecuta en background el pipeline completo (git → install → build → `pm2 restart` → verificación → post-deploy) y deja registrado cada paso en el historial de deployments del proyecto.

### Antes vs. ahora

**Antes (manual).** Cada deploy de ATLAS eran 4 pasos:

1. SSH al server y `cd /home/rpatic/ATLAS/`.
2. `git pull && pnpm build`.
3. Reiniciar `atlas-backend` y `atlas-frontend` a mano en PM2 View.
4. Aparte, correr `ATLAS_DOCS_BASE=/atlas/docs pnpm build:docs` (obligatorio, si no la doc no se publicaba).

**Ahora.** Hacés `git push` y nada más. El webhook dispara el pipeline completo:

```text
push → git pull → pnpm install → pnpm build → restart atlas-backend + atlas-frontend → verify online
                                                                                    → ATLAS_DOCS_BASE=/atlas/docs pnpm build:docs  (post-deploy)
```

Sin SSH, sin restart manual, sin acordarte del `build:docs`.

### Qué hace el pipeline

| Etapa | Acciones | En caso de fallo |
| --- | --- | --- |
| **git** | Verifica el árbol limpio (solo archivos trackeados) → `fetch` → `checkout` de la rama → `pull --ff-only` | Falla rápido; no se toca nada más |
| **install** | Comando configurado, o fallback al package manager detectado (`pnpm`/`npm`/`yarn`) | Falla; el build no corre |
| **build** | Comando configurado, o `<pm> run build` si el script existe; se salta si no hay ninguno | Falla; **PM2 no se reinicia** |
| **pm2** | Para cada nombre en `pm2_names`: `pm2 restart <name> --update-env`, luego espera a que quede `online` | Falla si algún proceso no llega a `online` |
| **post-deploy** | Comandos opcionales configurados; corren en secuencia después del restart | Nunca hace fallar el deploy; queda warning |

El pipeline es **no destructivo**: nunca corre `reset --hard`, `clean` ni `checkout .`. Si hay cambios locales en archivos trackeados dentro de `target_path`, el deploy aborta explícitamente.

<Info>
  Para grupos multi-proceso (por ejemplo `["atlas-backend", "atlas-frontend"]`), PM2 View valida **antes de tocar nada** que todos los procesos existan en PM2. Si alguno no existe, hay que arrancarlo manualmente una vez con su ecosystem file: el auto-start desde el pipeline todavía no está soportado.
</Info>

### Configuración en PM2 View (una sola vez por proyecto)

En el proyecto → pestaña **Config** → tarjeta **Automatic Deployment**:

| Campo | Valor de ejemplo (ATLAS) | Notas |
| --- | --- | --- |
| Automatic deployment | `ON` | Interruptor maestro; si está en OFF, los push se ignoran |
| GitHub Repository | `owner/ATLAS` | Copiado del URL `github.com/<owner>/<name>`; debe coincidir |
| Branch | `main` | Solo los push a esta rama disparan deploy |
| `target_path` | `/home/rpatic/ATLAS/` | Ruta absoluta al clone en el servidor |
| `pm2_names` | `["atlas-backend", "atlas-frontend"]` | Todos los procesos que hay que reiniciar juntos |
| Post-Deploy Actions | `pnpm build:docs` | Se ejecuta después del restart; falla → solo warning |

Con esa configuración, cada `git push` (código o documentación) regenera la doc automáticamente al final. El warning de "si no corrés `build:docs` la doc no se publica" deja de ser tarea manual.

<Tip>
  Los comandos post-deploy admiten variables inline al estilo `KEY=VALUE comando`. Por ejemplo, `ATLAS_DOCS_BASE=/atlas/docs pnpm build:docs` inyecta `ATLAS_DOCS_BASE` solo para ese comando, sin necesidad de exportarla en el entorno del servidor.
</Tip>

### Registrar el webhook en GitHub

En el repo → **Settings → Webhooks → Add webhook**:

| Campo | Valor |
| --- | --- |
| Payload URL | `https://gcmbigdata.online/pm2/api/webhooks/github` |
| Content type | `application/json` |
| Secret | `pm2-big-data` |
| SSL verification | **Enable SSL verification** (dejarlo por defecto) |
| Which events | **Just the push event** |
| Active | ✅ Marcado |

<Warning>
  El `Secret` **tiene que ser exactamente** el mismo valor que la variable `GITHUB_WEBHOOK_SECRET` que corre PM2 View en el servidor. Si no coincide, GitHub va a recibir `401 Invalid webhook signature` en cada entrega y ningún push disparará deploy.

  El secret actual de Big Data es `pm2-big-data`. Si se rota, hay que actualizarlo **en los dos lados** (env del server \+ webhook de cada repo) o los auto-deploys dejan de funcionar en silencio.
</Warning>

### Cómo se autentica git

PM2 View no usa deploy keys ni PATs guardados en el server. Cada operación de git dentro del pipeline usa un **token de instalación de la GitHub App**, minteado on-demand y con validez de 1 hora, scopeado al repo. Prerrequisito: la GitHub App de PM2 View tiene que estar instalada sobre el owner del repo. El paso a paso vive en [`docs/github-integration.md`](https://github.com/programadorisgod/pm2-view/blob/main/docs/github-integration.md) del repo de PM2 View.

### Qué pasa en cada entrega del webhook

| Código HTTP | Significado |
| --- | --- |
| `202` | Aceptado; el deployment se encoló (la respuesta trae los IDs) |
| `200` | Delivery duplicado (mismo `X-GitHub-Delivery`); replay idempotente, no se corre dos veces |
| `204` | Ignorado: evento no-push, o el repo/rama no coincide, o `Automatic deployment` está en OFF |
| `401` | Firma HMAC inválida (secret incorrecto) |

La firma se valida con HMAC-SHA256 sobre el cuerpo crudo del request, con comparación timing-safe. La idempotencia se garantiza por un `UNIQUE` sobre `X-GitHub-Delivery` en la tabla de deployments.

### Notificaciones por correo

Al terminar cada deployment (éxito o fallo), PM2 View manda un correo con el resultado al owner del proyecto y a la dirección configurada en `notify_email` (deduplicadas). El correo incluye estado, proyecto, `repo@branch`, commit SHA, etapa donde falló (si aplica), error y duración. La entrega usa SMTP; si el envío falla queda en logs pero **nunca** afecta el resultado del deployment.

### Troubleshooting

| Síntoma | Causa probable | Cómo resolverlo |
| --- | --- | --- |
| `401 Invalid webhook signature` | Secret distinto entre GitHub y el env de PM2 View | Igualar `GITHUB_WEBHOOK_SECRET` con el Secret del webhook |
| Push ignorado (`204`) | Repo/rama no coincide o `Automatic deployment` en OFF | Revisar que Config coincida exactamente con lo que llega de GitHub |
| Falla en git: `authentication` | La GitHub App no está instalada sobre el owner del repo | Instalar la App / revisar `github_installations` |
| Falla en git: `local modifications` | Hay cambios locales en archivos trackeados dentro de `target_path` | Limpiar/stashear cambios en el servidor |
| Falla en pm2: `process not found` | Un nombre de `pm2_names` no existe en PM2 | Arrancarlo una vez manualmente con su ecosystem file |
| Build falló, el proceso sigue con el PID viejo | Diseño: PM2 solo reinicia si el build fue exitoso | Arreglar el build y volver a deployar |

### PM2 Save

Permite ejecutar la persistencia del estado actual de PM2.

<Warning>
  Es **SUPER IMPORTANTE que lo realices cada que agregues un proyecto**, ya que este botón te permitirá guardar todos los procesos que se están ejecutando actualmente en el servidor a través de PM2.
</Warning>

Conceptualmente:

```bash
pm2 save
```

Esto permite guardar la lista actual de procesos para que pueda ser restaurada posteriormente.

### PM2 Startup

PM2 también permite configurar el arranque automático de los procesos cuando el servidor inicia.

Conceptualmente:

```bash
pm2 startup
```

El objetivo es que, después de un reinicio del servidor, los procesos previamente registrados puedan volver a levantarse automáticamente.

<Warning>
  Una vez realizas el paso de `pm2 save`, realizas el paso de `pm2 startup`. De lo contrario todo el trabajo será en vano **y tendrás que levantarlos manualmente en caso de reinicio**.
</Warning>

### Métricas del servidor

PM2 View también proporciona información relacionada con el estado de ejecución de las aplicaciones y del servidor. Esto permite tener una visión rápida del consumo de recursos y detectar comportamientos anómalos.
